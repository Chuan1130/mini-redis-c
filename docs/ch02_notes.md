# ch02_notes

## 本章定位

这一章的主题是：

“把上一章的数组版存储层，升级成哈希桶版存储层”

如果把上一章看成“先把存储层独立出来”，
那么这一章就是“在已经独立的存储层内部，第一次认真升级数据结构”。

## 本章目标

本章只做一件主线事情：

- 把 `db.*` 的内部从“固定数组 + 线性扫描”升级成“哈希桶 + 链表”

本章明确不做：

- 不新增更多命令
- 不做持久化
- 不做 TTL
- 不改客户端输入系统
- 不改 RESP
- 不大改网络层

## 本章完成后程序具备什么能力

和上一章相比，这一章最关键的变化不是“用户能看到的新命令”，
而是数据库内部查找方式变了：

- 仍然支持 `SET key value`
- 仍然支持 `GET key`
- `tcp_server.c` 基本不需要大改
- 但 `db.*` 不再依赖从头扫描整个数组
- 它会先根据 key 算哈希值，再定位桶，再在桶链里查找

## 本章代码思路

本章的代码思路可以分成 4 步：

1. 先保留原来的 `db_set` / `db_get` 接口
2. 再把 `Db` 的内部从数组改成桶数组
3. 为每个桶引入链表节点 `DbNode`
4. 让 `db_set` / `db_get` 通过“哈希 -> 定位桶 -> 遍历桶链”工作

这里有一个很重要的工程点：

- 接口基本没变
- 但实现已经升级了

这说明如果模块边界设计得好，底层替换可以不强行拖着上层一起大改。

## 关键设计分析

### 1. 为什么需要哈希函数

如果没有哈希函数，数据库就不知道：

- 一个 key 应该落到哪个桶

所以哈希函数的作用，可以简单理解成：

- 把任意 key 变成一个整数

拿到这个整数后，再对桶数量取模，就能得到桶下标。

### 2. 为什么还需要链表

哈希函数不是“神谕”。
不同 key 有可能落到同一个桶，这叫哈希冲突。

一旦冲突发生，我们总要想办法把多个 key 都存进去。

本章选的是最适合初学者理解的一种方式：

- 链地址法
- 也就是“同一个桶里的多个元素，用链表串起来”

### 3. 为什么 `tcp_server.c` 几乎不用改

因为上一章已经把存储层独立出来了。

服务端主流程只依赖：

- `db_set`
- `db_get`

它并不依赖：

- 底层到底是数组
- 还是哈希桶

所以本章能非常直观地体现一个重要思路：

- 把接口设计稳定
- 再让实现逐步升级

## 我作为初学者应该重点关注什么

建议你这章重点看下面 6 个点：

1. `Db` 结构体为什么从“记录数组”变成“桶数组”
2. `DbNode` 里的 `next` 指针为什么必须存在
3. `db_hash_key` 到底解决了什么问题
4. `db_bucket_index` 为什么要对桶数取模
5. `db_find_node_in_bucket` 为什么仍然要比较 key 内容
6. `db_set` 新插入时为什么用头插法

如果你把这 6 个点看明白，这一章最重要的知识就掌握了。

## 本章与上一章最关键的区别

上一章的重点是：

- 把存储层从服务端主文件中独立出来

这一章的重点是：

- 在独立存储层内部，把“数组实现”升级成“哈希桶实现”

简单说：

- 上一章解决“边界”
- 这一章解决“结构”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 端到端基础测试

```text
set foo bar
get foo
set foo baz
get foo
get missing
```

预期：

- 第一次 `set` 成功
- `get foo` 返回 `bar`
- 第二次 `set foo baz` 成功
- 再次 `get foo` 返回 `baz`
- `get missing` 返回错误

### 3. 精确匹配测试

```text
set foobar one
get foo
get foobar
```

预期：

- `get foo` 返回错误
- `get foobar` 返回 `one`

### 4. 模块级测试

可以写一个最小 C 程序，直接调用：

- `db_init`
- `db_set`
- `db_get`
- `db_free`

重点验证：

- 覆盖更新
- 不存在 key
- 桶冲突时仍能正确找回数据
- 容量上限仍然有效

## 旧代码如何保留

本章被替换掉的“大块旧实现”是上一章的数组版 `db.*`。

它们已经保存在：

```text
archive/ch02_legacy/db_before_hash.h
archive/ch02_legacy/db_before_hash.c
```

保留它们的目的不是继续参与主线编译，
而是方便以后对照：

- 数组版为什么简单
- 哈希桶版为什么查找路径更短

## 本章心得

这一章是第一次真正碰到“数据结构改变，但接口尽量不变”的场景。

这是非常值得你反复体会的一章，因为它会让你开始明白：

- 好的模块边界不是为了好看
- 而是为了让后续升级变得可控

如果上一章没有先把 `db.*` 拆出来，
那这一章就会被迫去改很多和存储本身无关的代码。

所以这两章其实是连在一起的：

- ch01 让你先学会分层
- ch02 让你看到分层之后，升级会有多自然

## 当前仓库下一步最自然的方向

下一步最自然的方向不是马上加很多命令，
而是继续把当前哈希表做得更完整一些，例如：

- 更系统地处理冲突和桶分布
- 讨论并实现最小可用的扩容 / rehash 思路
- 继续把 `db.*` 做成更稳的存储层
