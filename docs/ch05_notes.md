# ch05_notes

## 本章定位

这一章的主题是：

“在已有 SET / GET / DEL 主线基础上，补上 EXISTS 存在性检查”

如果说上一章主要解决的是“怎么把节点安全删掉”，
那么这一章主要解决的是：

- 并不是每次都要把 value 取出来
- 有时候我们只想知道“这个 key 在不在”

## 本章目标

本章只做一条很小但很自然的主线：

- 在 `db.*` 中加入 `db_exists`
- 在服务端命令层加入 `EXISTS key`

本章明确不做：

- 不新增很多字符串命令
- 不改协议格式
- 不做 TTL
- 不做持久化
- 不重写客户端
- 不重构网络层

## 本章实现了什么

这一章完成后，程序支持的最小字符串命令已经变成：

- `SET key value`
- `GET key`
- `DEL key`
- `EXISTS key`

其中 `EXISTS key` 的当前表现是：

- key 存在：返回 `1`
- key 不存在：返回 `0`

注意，这两个结果都属于“命令执行成功”，
所以它们都走成功响应，而不是错误响应。

## 代码思路

这一章的实现思路非常克制，只有 4 步：

1. 在 `include/db.h` 中增加 `db_exists`
2. 在 `src/db.c` 中复用现有桶查找逻辑实现存在性判断
3. 在 `src/tcp_server.c` 中加入 `EXISTS`
4. 保持客户端和协议层不变，直接复用现有响应打印逻辑

这样做的好处是：

- 改动范围很小
- 学习重点非常集中
- 你可以清楚看到“一个新命令是怎么接到现有存储层上的”

## 关键设计分析

### 1. 为什么 EXISTS 值得单独做一章

很多初学者在学 KV 数据库时，会先学：

- 写入
- 读取
- 删除

但其实“判断存在性”也是很常见的基础需求。

它之所以适合作为单独一章，是因为它能训练你理解：

- 命令不一定都要把 value 取出来
- 底层同一套查找逻辑，可以服务多个不同命令

### 2. 为什么 db_exists 不直接复用 db_get

从功能上说，`db_get` 也能间接判断存在性。

但本章还是单独提供 `db_exists`，原因是：

- `EXISTS` 不需要拿到 value
- 它只关心“有没有这个 key”
- 单独写一个更贴合语义的接口，对初学者更清楚

这样你以后回头看代码时，不会觉得：

- “为什么 EXISTS 还要先 GET 一次 value 再丢掉”

### 3. 为什么 EXISTS 的不存在返回 `0`，而不是 ERR

这是本章一个很值得注意的设计点。

`GET missing` 当前会返回错误，
因为它是在请求一个“值”，但值不存在。

而 `EXISTS missing` 问的问题本来就是：

- 在，还是不在

所以“不在”并不是命令执行失败，
而是这个命令的正常答案之一。

因此当前把它设计成：

- 存在 -> `1`
- 不存在 -> `0`

并且两者都走成功响应。

## 为什么这样设计

这一章选择这种实现方式，主要是为了兼顾三件事：

1. 不扩大协议复杂度
2. 不破坏现有客户端
3. 让命令语义比上一章更清楚一点

因为当前客户端已经支持：

- 成功时打印 payload
- 失败时打印 `(ERR)`

所以 `EXISTS` 只要返回 `"1"` 或 `"0"`，
就能在不改协议结构的前提下，把结果表达清楚。

## 关键数据流

本章 `EXISTS key` 的数据流是：

1. 客户端读取 `exists foo`
2. `tcp_client.c` 把它编码成当前请求 payload
3. 服务端收到请求并调用 `parse_req`
4. `tcp_server.c` 在 `do_request` 中识别到 `EXISTS`
5. `tcp_server.c` 调用 `db_exists`
6. `db_exists` 只扫描目标 key 所在的桶链
7. 找到则返回 `1`，否则返回 `0`
8. 服务端打包响应
9. 客户端打印结果

这一章最值得你注意的一点是：

- 新命令并没有新建一套数据结构路径
- 它只是很好地复用了当前哈希表查找逻辑

## 初学者最该注意的点

建议你重点看下面 6 个点：

1. `db_exists` 为什么只需要返回 `DbStatus`
2. `db_exists` 为什么不需要拿到 value
3. 为什么它仍然要先算桶，再只扫一个桶链
4. 为什么 `EXISTS missing` 返回 `0` 比返回错误更合理
5. 为什么这一章不需要改客户端协议结构
6. 为什么一个小命令也值得单独成章

## 容易犯错的点

这章最容易犯的错主要有这些：

1. 把 `EXISTS` 写成和 `GET` 一样，不存在就直接返回 ERR
2. 在 `db_exists` 里重复实现很多不必要的逻辑
3. 忘了复用现有桶查找路径，导致写出两套不一致逻辑
4. 为了一个小命令，顺手把协议层改复杂

这一章最重要的原则是：

- 只做这一章需要的最小改动

## 本章与上一章的区别

上一章的重点是：

- 节点如何安全删除

这一章的重点是：

- 如何在不取值的情况下判断 key 是否存在

简单说：

- ch04 重点是“删”
- ch05 重点是“查存在性”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 模块级测试

建议写一个最小 C 程序，直接调用：

- `db_init`
- `db_set`
- `db_exists`
- `db_del`
- `db_free`

重点验证：

- 已写入 key 时 `db_exists` 返回 OK
- 未写入 key 时 `db_exists` 返回 NOT_FOUND
- 删除后再查存在性，结果应变成 NOT_FOUND

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
exists foo
del foo
exists foo
exists missing
```

预期：

- `exists foo` 在删除前返回 `1`
- 删除后返回 `0`
- `exists missing` 直接返回 `0`

## 本章心得 / 复盘

这一章看起来很小，但它很适合帮助你建立一个经验：

- 一个成熟一点的命令层，往往不是靠“大改架构”长出来的
- 而是靠一个个小而清晰的命令慢慢补齐的

如果你能把这章看明白，你会更容易理解：

- 为什么接口设计要尽量稳定
- 为什么底层查找逻辑值得复用
- 为什么不是每次加命令都要大改协议

## 当前仓库下一步最自然的方向

下一步最自然的方向是：

“继续围绕字符串 KV 主线，补更清晰的结果表达或更多克制的基础命令能力”

也就是说，后面可以开始认真讨论：

- 哪些命令返回值更适合用明确的结果类型表达
- 当前响应模型是否需要继续细化

但这些都应该留到下一章，不在本章提前实现。
