# ch07_notes

## 本章目标

这一章的目标是：

“围绕当前字符串 KV 主线，补上最小过期时间能力”

也就是说，数据库不再把所有 key 都当成永久存在，
而是开始支持：

- 给 key 设置过期时间
- 过期后再访问时，把它当成不存在

## 本章实现了什么

本章新增了两个最小命令：

- `EXPIRE key seconds`
- `TTL key`

同时数据库内部也开始支持：

- 节点记录“有没有过期时间”
- 节点记录“绝对过期时刻”
- 在 `GET / EXISTS / DEL / TTL` 时做懒删除式过期检查

当前命令语义：

- `EXPIRE key seconds`
  - 成功设置：返回 `1`
  - key 不存在：返回 `0`
- `TTL key`
  - 返回 `>= 0`：还剩多少秒
  - 返回 `-1`：key 存在，但没有设置过期时间
  - 返回 `-2`：key 不存在

## 代码思路

这一章的实现思路分成 5 步：

1. 给 `DbNode` 增加过期相关字段
2. 在 `db.*` 中增加当前时间和过期判断辅助函数
3. 在读、查、删时，遇到已过期 key 就懒删除
4. 加入 `db_expire` 和 `db_ttl`
5. 在命令层接入 `EXPIRE` 和 `TTL`

这章有意没有实现复杂的后台主动清理线程，
而是先采用最容易讲清楚的“懒删除式过期”。

## 关键设计分析

### 1. 为什么要保存绝对过期时刻

这一章没有在节点里保存“还剩多少秒”，
而是保存：

- `expire_at_ms`

也就是一个绝对时间点。

这样做的好处是：

- 读取时只要比较 `now >= expire_at_ms`
- 查询 TTL 时只要算差值

### 2. 为什么先做懒删除，而不是主动过期

主动过期通常意味着：

- 后台定时扫描
- 独立时间结构
- 更复杂的调度逻辑

这对当前项目来说跨度太大。

所以这一章先做：

- 当某个 key 再次被访问时
- 如果发现它已经过期
- 就顺手把它删掉

这就是懒删除。

### 3. 为什么 db_get / db_exists 不再是“完全只读”

这一章非常值得注意的一点是：

- 以前 `db_get` / `db_exists` 看起来像只读查询
- 现在一旦发现 key 已过期，它们就会顺手删除节点

也就是说：

- 逻辑上是在“读”
- 但实现上可能会修改数据库

所以接口里的 `const Db *` 也必须调整掉。

## 为什么这样设计

这一章的设计目标是：

1. 尽量小步推进
2. 不引入太多新数据结构
3. 先把“时间语义”接进已有主线

因此我没有一下子做：

- 复杂定时器
- 主动清理循环
- 持久化里的过期恢复

而是先把最基础的：

- 设置过期
- 查询过期
- 访问时处理过期

这一条主线走通。

## 关键数据流

以 `EXPIRE foo 1` 为例，本章的数据流是：

1. 客户端发出 `expire foo 1`
2. 服务端命令层解析出 `key=foo`、`seconds=1`
3. `db_expire` 找到节点
4. 把 `has_expire=true`
5. 把 `expire_at_ms=当前时间+1000`
6. 返回整数 `1`

以“过期后的 `GET foo`”为例：

1. 客户端发出 `get foo`
2. `db_get` 在目标桶里找到节点
3. 先比较当前时间和 `expire_at_ms`
4. 发现已经过期
5. 先把节点从桶链中摘掉并释放
6. 再把这次查询当成“不存在”返回

## 初学者最该注意的点

建议你重点看下面 8 个点：

1. `has_expire` 和 `expire_at_ms` 分别表示什么
2. 为什么要保存绝对时间，而不是剩余时间
3. 为什么 `db_get` / `db_exists` 现在可能修改数据库
4. 什么叫“懒删除式过期”
5. 为什么 `TTL` 要区分 `-1` 和 `-2`
6. 为什么 `EXPIRE` 返回 `1/0`
7. 为什么 `SET` 覆盖旧值时要清掉旧的过期时间
8. 为什么这一章先不做主动过期线程

## 容易犯错的点

这一章最容易出错的地方有这些：

1. 给 key 设置过期时间后，`GET` 还忘了检查过期
2. `EXISTS` 和 `GET` 对已过期 key 的表现不一致
3. 删除已过期节点时忘了同步减 `size`
4. `TTL` 把“不存在”和“没有过期时间”混在一起
5. `SET` 覆盖旧 key 时忘了清理旧 TTL

## 本章与上一章的区别

上一章的重点是：

- 把响应语义表达清楚

这一章的重点是：

- 把“时间”这件事接进数据库主线

简单说：

- ch06 重点是“结果怎么表达”
- ch07 重点是“key 会不会过期”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 模块级测试

重点验证：

- 设置过期时间前 `TTL` 返回 `NO_EXPIRE`
- 设置过期时间后 `TTL` 返回正数
- 等待过期后 `GET / EXISTS / DEL / TTL` 都表现为不存在
- `EXPIRE key 0` 会让 key 立即失效

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
expire foo 1
ttl foo
exists foo
```

等待 2 秒后再验证：

```text
get foo
exists foo
ttl foo
```

还要补充：

```text
set bar baz
expire bar 0
exists bar
```

## 本章心得 / 复盘

这一章非常关键，因为它让数据库第一次真正有了“时间维度”。

从这一章开始，你需要建立一个新直觉：

- 数据库里的 key 不只是“有没有”
- 还要问“它现在是不是还有效”

这会直接影响后面的：

- 读取
- 删除
- 存在性检查
- 持久化

所以虽然这章只多了 `EXPIRE` 和 `TTL`，
但它实际上是给后续章节铺了很重要的一层地基。
