# ch06_notes

## 本章目标

这一章的目标是：

“让当前命令层的结果表达更清晰”

在上一章结束时，项目已经支持：

- `SET`
- `GET`
- `DEL`
- `EXISTS`

但这些命令的返回值语义并不统一：

- `SET` 更像简单成功
- `GET` 更像字符串结果
- `DEL` 和 `EXISTS` 更像整数结果
- `GET missing` 又更像空结果

所以本章不去加新命令，而是先把“响应是什么”这件事讲清楚。

## 本章实现了什么

本章主要完成了三件事：

1. 在 `codec.*` 中引入明确的响应类型系统
2. 在服务端用 `Resp` 表达命令语义结果
3. 在客户端按不同类型正确打印结果

当前响应类型包括：

- `RESP_OK`
- `RESP_ERR`
- `RESP_STR`
- `RESP_INT`
- `RESP_NIL`

这意味着现在客户端已经能更清楚地区分：

- 简单成功
- 错误
- 字符串
- 整数
- 空结果

## 代码思路

这一章的代码思路可以分成 5 步：

1. 先在 `include/codec.h` 定义 `RespType`、`Resp`、`RespView`
2. 再在 `src/codec.c` 里实现新的响应编码和解析
3. 修改 `src/tcp_server.c`，让命令层直接返回 `Resp`
4. 修改 `src/tcp_client.c`，按响应类型打印结果
5. 保持请求协议、网络层和数据库结构不变

这样做的好处是：

- 改动集中在“结果表达”这一层
- 不会把这一章扩散成大重构
- 你能明显看见“语义层”和“存储层”在分工

## 关键设计分析

### 1. 为什么需要 RespType

如果服务端永远只返回：

- 成功 / 失败

那一旦命令变多，客户端就会越来越难分辨：

- 这是一个字符串结果？
- 还是一个整数结果？
- 还是“值不存在”？

所以本章把“结果的种类”显式化了。

### 2. 为什么 GET missing 适合返回 NIL

`GET missing` 并不是“命令执行崩了”，
而是“查询结果为空”。

所以把它表达成 `RESP_NIL`，
会比直接当作 ERR 更符合数据库语义。

### 3. 为什么 DEL / EXISTS 更适合返回整数

这两个命令本身更像是在回答：

- 影响了几个 key
- 是否存在

这类问题天然适合整数表达。

因此这一章把它们统一成 `RESP_INT`，
而不是继续勉强塞进字符串或 OK/ERR。

## 为什么这样设计

这章的设计重点不是“尽量接近真正 Redis 协议”，
而是先让当前自定义协议内部变得更清楚。

也就是说：

- 我们还保留自定义 framing
- 还保留自定义 request 编码
- 但 response 已经先学会“按类型表达”

这是一个很自然的中间阶段。

## 关键数据流

本章之后，一条命令的响应数据流是：

1. 客户端发请求
2. 服务端解析参数
3. `do_request` 构造 `Resp`
4. `make_resp` 按 `RespType` 编码成 response payload
5. `proto.*` 负责发完整包
6. 客户端通过 `recv_msg` 收完整响应
7. `parse_resp` 解析响应类型和内容
8. 客户端按类型打印

这章最重要的变化就在第 3 到第 8 步。

## 初学者最该注意的点

建议你重点看下面 7 个点：

1. `Resp` 和 `RespView` 的区别
2. 为什么 `Resp` 不是网络字节，而是“语义对象”
3. 为什么 `RESP_NIL` 不能简单等同于 `RESP_ERR`
4. 为什么 `DEL` / `EXISTS` 更适合用整数类型
5. `make_resp` 为什么要先算 body 长度
6. `parse_resp` 为什么必须按 type 分支解析
7. 客户端打印为什么要单独提成 `print_resp`

## 容易犯错的点

本章最容易出错的地方有这些：

1. 仍然把所有响应当成同一种格式解析
2. 忘了 `RESP_INT` 是 8 字节，不是 4 字节
3. 把 `GET missing` 继续当成错误
4. 改了服务端响应格式，却忘了同步改客户端解析
5. 只改注释，不真正让命令层返回不同类型

## 本章与上一章的区别

上一章的重点是：

- 增加 `EXISTS`

这一章的重点是：

- 不增加很多新命令，而是先把现有命令的结果表达整理清楚

简单说：

- ch05 重点是“多一个命令”
- ch06 重点是“结果类型更清楚”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 编解码测试

重点测试：

- `RESP_OK`
- `RESP_ERR`
- `RESP_STR`
- `RESP_INT`
- `RESP_NIL`

确认 `make_resp` 和 `parse_resp` 的行为一致。

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
get foo
get missing
exists foo
exists missing
del foo
del foo
```

预期：

- `set foo bar` 显示 `OK`
- `get foo` 显示 `bar`
- `get missing` 显示 `(nil)`
- `exists foo` 显示 `1`
- `exists missing` 显示 `0`
- `del foo` 第一次显示 `1`
- `del foo` 第二次显示 `0`

## 本章心得 / 复盘

这一章很值得你建立一个意识：

- 数据库实现不只是“把数据存进去”
- 还包括“怎样把结果准确地告诉客户端”

如果返回语义混乱，命令越多，客户端越难写，调试也越难做。

所以这一章虽然看起来不像哈希表、过期时间那样“功能很大”，
但它其实是在给后面章节打协议和命令语义的基础。
