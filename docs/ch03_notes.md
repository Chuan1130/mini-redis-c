# ch03_notes

## 本章定位

这一章的主题是：

“让当前哈希表开始具备最小可用的扩容 / rehash 能力”

如果把上一章看成“先把数组升级成哈希桶”，
那么这一章就是“继续把这个哈希桶推进到更完整的工程版本”。

## 本章目标

本章只做一件主线事情：

- 在 `db.*` 内部加入最小可用的扩容 / rehash

本章明确不做：

- 不新增更多命令
- 不做 TTL
- 不做持久化
- 不改 RESP
- 不重写客户端
- 不大改 `tcp_server.c`

## 本章完成后程序具备什么能力

和上一章相比，这一章最关键的新能力是：

- 哈希表不再永远固定在同一桶数
- 当负载变高时，会扩到更多桶
- 扩容后旧数据仍然能被正确查回
- `tcp_server.c` 基本不需要跟着重写

也就是说，这一章的重点不是“新增用户命令”，
而是“让当前存储层更像一个真正会成长的哈希表”。

## 本章代码思路

这一章的代码思路可以分成 5 步：

1. 先保留现有 `db_set` / `db_get` 接口不变
2. 再让 `Db` 记录“当前激活桶数”
3. 写一个判断“是否该扩容”的辅助逻辑
4. 写一个真正负责重新分布节点的 `rehash` 过程
5. 在写入前，如果负载偏高，就先 rehash 再插入

这样做的好处是：

- 上层服务端逻辑几乎不用动
- 但底层哈希表已经不再是死的固定桶数

## 关键设计分析

### 1. 为什么需要 rehash

哈希表并不是“有桶就够了”。

如果桶数量固定，而元素不断增加，就会出现：

- 越来越多 key 落到同一个桶
- 同一个桶的链表越来越长
- 查找成本又开始升高

所以哈希表真正想保持查找效率，
就必须在合适的时候扩容，再把旧数据重新分布。

这件事就叫 rehash。

### 2. rehash 到底在做什么

很多初学者会以为 rehash 是“把数据复制一遍”。

其实本章的 rehash 更准确地说是在做：

1. 增加当前启用的桶数量
2. 遍历原来的所有节点
3. 用新的桶数量重新计算每个 key 应落到哪里
4. 把节点重新挂接到新的桶链上

注意：

- 节点本身仍然是原来的节点
- 变化的是“它挂在哪个桶”和“它的 next 指针”

### 3. 为什么本章仍然不把桶数组做成动态堆分配

这是一个刻意的教学取舍。

如果这一章同时处理：

- 节点内存管理
- 桶数组本身的动态分配
- 扩容策略
- rehash 过程

那学习负担会明显变重。

所以本章先采用：

- 固定上限桶数组
- 动态变化“当前启用桶数”

这样仍然可以把 rehash 的核心思路讲清楚，
同时避免把问题一下子做得太杂。

## 我作为初学者应该重点关注什么

建议你这章重点看下面 7 个点：

1. `Db` 结构体为什么新增 `bucket_count`
2. `db_should_rehash_before_insert` 在判断什么
3. 为什么阈值不是等桶完全塞满才扩容
4. `db_next_bucket_count` 为什么通常按翻倍增长
5. `db_rehash` 为什么要先保存 `next`
6. 为什么 rehash 后节点本身不需要重新申请
7. 为什么 `tcp_server.c` 基本不需要改

如果这 7 个点你看懂了，本章最重要的知识就掌握了。

## 本章与上一章最关键的区别

上一章的重点是：

- 把数组版存储层升级成固定桶数哈希表

这一章的重点是：

- 让固定桶数哈希表开始具备扩容 / rehash 能力

简单说：

- ch02 解决“从数组到哈希桶”
- ch03 解决“哈希桶如何开始动态成长”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 模块级测试

建议写一个最小 C 程序，直接调用：

- `db_init`
- `db_set`
- `db_get`
- `db_free`

重点验证：

- 覆盖更新仍然正确
- 插入大量 key 后仍然都能查回
- 插入足够多元素后，`bucket_count` 会增长
- rehash 后旧数据不丢失

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
get foo
set foo baz
get foo
get missing
```

以及：

```text
set foobar one
get foo
get foobar
```

预期行为应该和上一章保持一致，
说明底层虽然升级了，但上层接口行为没有被破坏。

## 本章心得

这一章非常值得你反复体会的一点是：

- 很多数据结构不是“写出来就结束”
- 它们往往还有“规模变大后怎么办”的第二层问题

上一章你学到的是：

- 哈希函数
- 桶
- 冲突
- 链表

这一章你开始接触的是：

- 负载变高怎么办
- 桶不够用了怎么办
- 旧数据如何迁移

这也是为什么这一章虽然没有加新命令，
但它依然是一次很重要的升级。
