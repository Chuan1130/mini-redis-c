# ch08_notes

## 本章目标

这一章的目标是：

“围绕当前字符串 KV 主线，补上最小快照持久化能力”

前面几章已经把数据库在内存里的行为做出来了，
但只要服务端一退出，数据就全部消失。

所以这一章开始解决：

- 怎样把当前数据库保存到本地文件
- 怎样在服务端重启时再把它读回来

## 本章实现了什么

这一章新增了：

- `SAVE` 命令
- 服务端启动时自动尝试加载快照
- `persist.*` 模块

当前快照会保存：

- key
- value
- 是否设置过期时间
- 过期时间的绝对时刻

当前快照会跳过：

- 保存时已经过期的数据
- 加载时已经过期的数据

## 代码思路

这一章的实现思路可以分成 6 步：

1. 新建 `persist.h` / `persist.c`
2. 约定一个最小二进制快照格式
3. 遍历当前数据库，把有效节点写入文件
4. 启动时读取文件，恢复出新的临时数据库
5. 恢复成功后再替换主数据库
6. 在命令层增加 `SAVE`

这章有一个很重要的取舍：

- 先只做“整库快照”
- 不做复杂 AOF
- 不做后台自动保存

## 关键设计分析

### 1. 为什么单独拆出 persist.*

这一章没有把保存和加载硬塞进 `db.c` 或 `tcp_server.c`，
而是单独拆出 `persist.*`。

原因是：

- `db.*` 应该专注于“数据怎么存”
- `persist.*` 应该专注于“数据怎么落盘”
- `tcp_server.c` 应该专注于“什么时候触发保存/加载”

这能让职责更清楚。

### 2. 为什么加载时先恢复到临时数据库

这是这一章很值得你注意的一个工程点。

如果直接把文件内容一点点写进当前主数据库，
一旦中途文件损坏或读取失败，就会出现：

- 原数据库被改了一半
- 新数据库又没完全加载好

所以这一章采取的方式是：

1. 先把文件加载到临时 `Db tmp`
2. 全部成功后
3. 再用 `tmp` 替换主数据库

这会安全得多。

### 3. 为什么保存绝对过期时刻，而不是剩余秒数

这一章延续上一章的设计：

- 节点内部保存的是绝对过期时刻

所以快照里也直接保存绝对过期时刻。

这样加载时只需要判断：

- 当前时间和这个绝对时刻相比，是否已经过期

逻辑会比保存“还剩多少秒”更直观。

## 为什么这样设计

这一章的设计目标是：

1. 先把“落盘和恢复”主线走通
2. 尽量避免大改现有结构
3. 保持实现足够小，适合初学者回看

因此我没有在这一章做：

- AOF
- 自动周期保存
- 后台线程保存
- 崩溃恢复优化

这些都属于后续可扩展主题，
不适合和“最小快照持久化”混在一章里。

## 关键数据流

### SAVE 的数据流

1. 客户端输入 `save`
2. 服务端命令层识别到 `SAVE`
3. `persist_save` 遍历当前数据库
4. 把有效节点写入快照文件
5. 返回 `OK`

### 启动恢复的数据流

1. 服务端启动
2. `db_init` 初始化空数据库
3. `persist_load` 尝试打开快照文件
4. 如果文件存在，就把数据恢复到临时数据库
5. 恢复成功后，用临时数据库替换主数据库
6. 服务端开始对外提供服务

## 初学者最该注意的点

建议你重点看下面 8 个点：

1. 为什么快照文件要先写魔数
2. 为什么要单独写 `write_u32_be / read_u32_be`
3. 为什么持久化要跳过已过期数据
4. 为什么加载时要先恢复到临时数据库
5. 为什么 `SAVE` 这一章只做手动触发
6. 为什么服务端启动时加载失败只打印 warning，不直接崩溃
7. 为什么快照里保存绝对过期时刻
8. 为什么 `persist.*` 不直接替代 `db.*`

## 容易犯错的点

这一章最容易出错的地方有这些：

1. 文件里保存了已过期数据，却在加载时忘了丢掉
2. 只保存 key/value，忘了保存过期时间
3. 加载失败时把主数据库污染成半成品
4. 读写整数时忘了统一字节序
5. 修改 Makefile 后忘了把 `persist.c` 编译进去

## 本章与上一章的区别

上一章的重点是：

- 给 key 加上时间语义

这一章的重点是：

- 让数据库状态不只活在内存里

简单说：

- ch07 重点是“数据什么时候失效”
- ch08 重点是“数据怎么留下来”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 模块级测试

重点验证：

- 保存正常 key
- 保存带过期时间的 key
- 跳过已过期 key
- 再加载后，数据和 TTL 仍然合理

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set persist_key persist_value
set temp soon
expire temp 1
save
```

重启服务端并等待已过期 key 失效后，再验证：

```text
get persist_key
get temp
exists temp
ttl temp
```

预期：

- `persist_key` 可以恢复
- `temp` 不会被错误恢复成有效 key

## 本章心得 / 复盘

这一章很适合作为当前学习项目的“核心主线收束章”。

因为到这里为止，你已经把一个最小数据库最关键的几件事都走通了：

- 能收命令
- 能执行命令
- 能把数据存在内存里
- 能处理过期
- 能把数据保存下来
- 能在重启后恢复

它当然还远不是完整 Redis，
但对这个《Build Your Own Redis》式学习项目来说，
核心主线已经是完整闭环了。
