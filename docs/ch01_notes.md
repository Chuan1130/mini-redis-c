# ch01_notes

## 本章定位

这一章的主题是：

“把当前项目里的内存 KV 存储层正式独立出来”

上一章我们主要做的是整理和注释增强。
这一章开始，项目第一次真正从“一个大文件里的演示版实现”，走向“有清晰模块边界的可迭代实现”。

## 本章目标

这一章的唯一主目标是：

- 把原来直接写在 `tcp_server.c` 里的内嵌存储逻辑，提取到 `db.*` 模块里

注意，这里的关键词是“独立”和“理清边界”，不是“堆更多功能”。

本章明确不做：

- 不引入哈希表
- 不新增更多命令
- 不做持久化
- 不切换到 RESP 协议

## 本章完成后程序新增了什么能力

和上一章相比，本章最关键的新能力不是“命令变多了”，而是：

- 服务端有了独立的存储层接口
- `SET` 现在会正确覆盖旧值，而不是一味追加
- 存储容量到上限时，会返回清晰失败
- `GET` 会按“长度相等且内容相等”匹配 key，避免简单前缀误判

## 本章代码思路

这一章的代码思路其实很朴素，可以概括成三步：

1. 先定义一套存储层接口
2. 再把旧的数组型数据库实现搬到 `db.*`
3. 最后让 `tcp_server.c` 只通过接口调用数据库

这样做以后，服务端主程序不再需要知道：

- 记录存在数组的第几个位置
- 如何比较 key
- 如何覆盖旧 value
- 容量满了怎么办

这些细节都转移到了 `db.c` 里。

## 现在的数据流怎么走

### 1. 客户端

客户端还是和上一章一样：

1. 读取终端输入
2. 编码成请求
3. 发送给服务端

### 2. 服务端主流程

服务端仍然负责：

1. 接收连接
2. 用 `poll` 等待事件
3. 读取完整请求
4. 调用 `parse_req` 解析参数
5. 进入命令执行层

### 3. 新增的存储层

不同点在这里：

- 以前 `SET/GET` 直接操作 `tcp_server.c` 里的全局数组
- 现在 `SET/GET` 会调用 `db_set` / `db_get`

这样服务端主程序只知道“我要存值、我要取值”，
而不知道底层具体怎么保存。

## 关键设计分析

### 1. 为什么 `db.h` 里要显式保存长度

因为如果只把 key/value 当成普通 C 字符串处理，
很容易出现“前缀相同却被误判为同一个 key”的问题。

例如：

- `foo`
- `foobar`

如果比较方式不严谨，就可能把它们搞混。

所以本章故意让 `DbEntry` 同时保存：

- 指针
- 长度

这一步虽然简单，但对初学者非常重要，因为它让你开始意识到：

“字符串比较”和“字节序列比较”不是同一件事。

### 2. 为什么 `db_set` 要复制数据

请求参数来自网络请求缓冲区。
而请求缓冲区在一轮命令处理结束后就会被释放。

所以数据库不能偷懒保存原指针，必须复制出自己的副本。

这是 C 语言里非常典型、也非常容易错的地方：

- 你必须想清楚一块内存由谁拥有
- 谁负责释放
- 它能活多久

### 3. 为什么这一章仍然保留数组实现

因为这章的任务是“分层”，不是“性能优化”。

如果这章一口气同时做：

- 抽存储层
- 换哈希表
- 改协议
- 增命令

那你很难判断每一处改动到底在解决什么问题。

所以本章故意保持数组实现不变，只修正两个核心行为：

- 覆盖更新
- 精确匹配

这就是“按章节推进”的意义。

## 我作为初学者应该关注的点

建议你回头看代码时，优先关注下面 5 个点：

1. `tcp_server.c` 里 `do_request` 的职责变轻了，它只负责命令分发。
2. `db_set` 为什么不能直接保存请求里的指针。
3. `db_get` 为什么返回内部指针而不是新复制一份。
4. `db_find_index` 为什么现在虽然慢，但仍然合理。
5. `archive/ch01_legacy/` 中旧版 `tcp_server` 和新版主线相比，到底简化了哪里、清晰了哪里。

## 为什么这一章先不做哈希表

因为本章的主要学习目标是“分层”和“行为正确性”，不是“性能”。

如果现在一口气把事情变成：

- 抽模块
- 改接口
- 上哈希表
- 增加新命令

那学习难度会一下子抬高，不利于看清每一步到底解决了什么问题。

所以这一章故意只做到：

- 先把边界拆清楚
- 先把覆盖更新和精确匹配做对

## 本章如何测试

### 1. 基础写入读取

```text
set foo bar
get foo
```

预期：

- `set foo bar` 成功
- `get foo` 返回 `bar`

### 2. 覆盖更新

```text
set foo bar
set foo baz
get foo
```

预期：

- 第二次 `set` 会覆盖旧值
- `get foo` 返回 `baz`

### 3. 不存在的 key

```text
get missing
```

预期：

- 返回错误

### 4. 精确匹配 key

```text
set foobar one
get foo
get foobar
```

预期：

- `get foo` 返回错误
- `get foobar` 返回 `one`

### 5. 数据库容量上限

这一项不一定非要走客户端批量灌数据。
更适合用一个最小 C 测试程序直接调用 `db_set`：

- 先把数据库填到上限
- 再尝试插入一个新 key
- 预期返回 `DB_STATUS_FULL`

## 旧代码如何保留

本章涉及两类旧代码：

### 1. 旧的文本命令实验逻辑

例如 `tcp_server.c` 中保留的旧 `PING / ECHO` 响应构造路径。

这一类旧逻辑：

- 先原地保留
- 用注释说明它不是当前主路径

### 2. 原来写在 `tcp_server.c` 里的内嵌存储实现

这一类属于被本章正式替换的旧实现。

为了让主线代码更清楚，本章把替换前的版本保存到：

```text
archive/ch01_legacy/tcp_server_before_db_split.c
```

这样你后面既能看新版主线，也能回头对照旧实现。

## 本章心得

这一章看起来没有加很多“用户能看到的新功能”，
但它实际上很关键，因为它让项目开始出现真正的模块边界。

从学习角度说，这一章最大的收获不是“又多支持了一个命令”，
而是你会开始看到：

- 什么叫接口
- 什么叫实现
- 什么叫把职责从主流程中剥离出去

以后你再看更复杂的系统时，这种“先分清层次，再谈功能”的思路会非常有用。

## 本章和上一章最关键的区别

上一章重点是：

- 建立文档入口
- 补中文教学注释
- 看懂当前代码

这一章重点是：

- 真的开始建立模块边界
- 让“服务端主流程”和“存储层”分开

也就是说：

上一章更像“整理认路”，
这一章更像“正式搭建一个可以继续生长的结构”。
