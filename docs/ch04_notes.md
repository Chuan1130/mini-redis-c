# ch04_notes

## 本章定位

这一章的主题是：

“在可扩容哈希表基础上，补上删除能力和节点生命周期管理”

如果说上一章主要在解决“哈希表如何长大”，
那么这一章主要在解决“节点如何被安全移除”。

## 本章目标

本章只做一条主线：

- 在 `db.*` 中加入最小删除能力
- 再把这个能力通过服务端命令层暴露成 `DEL key`

本章明确不做：

- 不增加一大批新命令
- 不做 TTL
- 不做持久化
- 不改 RESP
- 不重写客户端
- 不重构网络层

## 本章完成后程序具备什么能力

这一章完成后，程序已经具备：

- `SET key value`
- `GET key`
- `DEL key`

更具体地说：

- 如果 key 存在，`DEL key` 可以把它从哈希桶链里摘掉
- 删除后再次 `GET`，会返回不存在
- 删除时会正确释放节点内部的 `key/value/node` 内存
- 数据库内部的 `size` 也会同步减少

## 本章代码思路

这一章的实现思路很克制，只有 4 步：

1. 在 `include/db.h` 中增加 `db_del`
2. 在 `src/db.c` 中实现删除节点逻辑
3. 在 `src/tcp_server.c` 的命令分发里增加 `DEL`
4. 保持协议层和客户端都不变

这样做的目的，是把注意力集中在：

- 链表节点如何删除
- 桶头删除和中间删除有什么区别
- 删除后内存如何释放

## 关键设计分析

### 1. 为什么删除能力值得单独做一章

初学者常常会觉得：

- 能 `SET`
- 能 `GET`

好像数据库就差不多了。

但实际上，删除操作会第一次真正逼你面对：

- 链表摘链
- 内存释放
- 数据结构一致性维护

所以 `DEL` 虽然看起来只是多了一个命令，
但它背后训练的是“指针操作是否稳定”。

### 2. 删除链表节点为什么容易出错

在哈希表里，真正存数据的是每个桶里的链表。

删除时最常见的坑有两个：

1. 忘了处理“删除桶头节点”
2. 忘了在删除后释放 `key/value/node`

如果只会处理中间节点，而不会处理桶头节点，
那么代码在某些 key 上就会坏。

如果只把节点从链表里摘掉，但不释放内存，
那就是典型的内存泄漏。

### 3. 为什么这一章不用更花哨的删除写法

这章我刻意在 `db_del` 中使用了最直观的：

- `prev`
- `node`

这种写法。

原因很简单：

- 对初学者最容易跟踪数据流
- 你能直接看见“前一个节点”和“当前节点”是怎么移动的
- 桶头节点和中间节点的区别也更清楚

这比一上来就写得很技巧化，更适合教学。

## 我作为初学者应该重点关注什么

建议你这章重点看下面 6 个点：

1. `db_del` 为什么要先算桶，再只扫这个桶链
2. `prev == NULL` 代表什么
3. 删除桶头节点和删除中间节点有什么区别
4. 为什么要把释放节点逻辑抽成 `db_free_node`
5. 删除后为什么必须 `db->size--`
6. 为什么 `tcp_server.c` 只要加一个 `DEL` 分支就够了

如果这 6 个点看懂了，这一章就掌握住了。

## 本章与上一章最关键的区别

上一章的重点是：

- 让哈希表在数据增多时可以扩容 / rehash

这一章的重点是：

- 让哈希表在数据不再需要时，可以安全删除节点

简单说：

- ch03 解决“表怎么长大”
- ch04 解决“节点怎么移除”

## 本章测试方法

### 1. 编译测试

```bash
make
```

### 2. 模块级测试

建议写一个最小 C 程序，直接调用：

- `db_init`
- `db_set`
- `db_get`
- `db_del`
- `db_free`

重点验证：

- 删除存在 key 成功
- 删除不存在 key 返回 `DB_STATUS_NOT_FOUND`
- 删除后再次 `GET` 返回不存在
- 删除桶头节点和中间节点都能正确工作
- 删除后 `size` 会减少

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
get foo
del foo
get foo
```

再验证：

```text
set a 1
set b 2
del a
get a
get b
```

预期：

- 删除成功返回 `OK`
- 删除后再查同一个 key 会返回错误
- 删除一个 key 不应影响别的 key

## 本章旧代码如何保留

这一章没有出现“需要整段替换掉的大型旧实现”。

原因是：

- 当前主线仍然是同一份 `db.c`
- 我们只是在它上面继续补 `db_del`
- 并没有把整个存储层换成另一种完全不同的实现

所以这一章不额外新建 `archive/ch04_legacy/` 来存代码快照。

如果后续某一章真的大规模替换了当前 `db.*`，
再按规则移动到 `archive/chXX_legacy/` 会更合适。

## 本章心得

这一章非常值得你建立一个直觉：

- 数据结构不仅要“能加进去”
- 还要“能安全拿出来”

很多初学者写哈希表时，写入和查询都能跑，
但一到删除就开始出错。

原因通常不是算法太难，
而是对指针关系和内存生命周期还没有形成稳定感觉。

所以这一章虽然功能上只多了一个 `DEL`，
但它训练的是非常核心的基本功。
