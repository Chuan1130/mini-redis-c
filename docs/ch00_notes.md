# ch00_notes

## 本章定位

这一章不是新增功能章，而是“项目整理章”。
目标是把当前仓库整理成适合继续按章节学习和迭代的状态。

## 当前实现已经做到了什么

当前代码已经形成了一个最小 Redis 风格闭环：

1. 客户端读取终端输入。
2. 客户端把输入拆成参数并编码成请求 payload。
3. 客户端再给 payload 外面包上一层长度前缀后发送给服务端。
4. 服务端先读取长度，再读取完整请求体。
5. 服务端解析请求参数。
6. 服务端执行最小命令集 `SET/GET`。
7. 服务端把执行结果编码为响应并返回给客户端。
8. 客户端解析响应状态并打印结果。

## 当前代码结构如何理解

### 1. `proto.*`

这一层只关心“怎么把一整条消息收全、发全”。
它不知道消息内容是 `SET` 还是 `GET`，只负责最外层的包边界。

### 2. `codec.*`

这一层关心“payload 里面到底长什么样”。
比如请求里有几个参数、每个参数多长，都是在这里解析的。

### 3. `tcp_client.c`

这一层是学习用客户端。
它模拟 Redis 客户端，把命令发给服务端，再把响应打印出来。

### 4. `tcp_server.c`

这是当前最重要的主线文件。
里面把网络循环、请求处理和极简数据库放在一起，方便一开始学习完整数据流。
但随着功能增加，后面需要逐步拆出更清晰的边界。

## 为什么这一步先补注释

因为项目已经不是“只有几十行 TCP 演示”了。
现在代码中同时有：

- 事件循环
- 长度前缀协议
- 请求编解码
- 命令分发
- 内存存储

如果这些边界不先讲清楚，下一章再进入数据结构层时，阅读难度会明显上升。

## 当前遗留问题

### 1. 存储层仍然过于简陋

- 使用固定数组保存键值对
- `SET` 没有认真处理覆盖
- `GET` 是线性扫描

这说明当前的“数据库层”还只是教学起步版。

### 2. 旧逻辑还留在服务端文件里

`tcp_server.c` 里还保留了旧的 `PING / ECHO` 响应构造逻辑。
这段代码现在不在主执行路径上，但保留它有助于理解项目是如何从“文本命令实验版”走到“结构化请求版”的。

后续如果它开始影响阅读，可以归档到：

```text
archive/ch01_legacy/
```

## 如何编译


## 如何运行

先开服务端：

```bash
./server
```

再开客户端：

```bash
./client
```

## 如何测试当前阶段

最小手工测试：

```text
set foo bar
get foo
get missing
```

预期现象：

- `set foo bar` 返回成功
- `get foo` 返回 `bar`
- `get missing` 返回错误
