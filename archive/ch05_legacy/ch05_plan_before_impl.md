## 下一章目标

下一章建议聚焦在：

“继续围绕当前字符串 KV 主线，补更完整但仍然克制的基础命令能力”

当前已经有：

- `SET`
- `GET`
- `DEL`

在这个基础上，最自然的下一步是继续补一个很小、很清晰、很适合教学的命令，
例如 `EXISTS key`。

## 下一章结束后程序应具备什么能力

如果下一章按计划完成，程序应该具备这些能力：

- 继续支持 `SET key value`
- 继续支持 `GET key`
- 继续支持 `DEL key`
- 新增存在性检查能力，例如 `EXISTS key`

理想情况下：

- key 存在时返回成功
- key 不存在时返回错误，或者返回明确的存在性结果

这一章的重点不是做复杂协议，
而是继续把命令层和存储层配合走稳。

## 需要新增或修改哪些文件

建议最小范围如下：

- 修改 `include/db.h`
  - 如果需要，增加只读存在性查询接口，例如 `db_exists`
- 修改 `src/db.c`
  - 复用当前查找逻辑实现存在性判断
- 修改 `src/tcp_server.c`
  - 在命令分发中增加 `EXISTS`
- 更新 `README.md`
  - 更新支持命令和阶段说明
- 新建或更新 `docs/ch05_notes.md`
  - 记录下一章设计、测试和学习重点

## 哪些内容不能提前实现

为了保持章节清晰，下一章不应该提前做这些事：

- 不要一口气加很多新命令
- 不要做 TTL / 过期

- 不要重写客户端

下一章只围绕“再补一个最小基础命令”展开。

## 如何测试下一章

下一章测试建议分成三层：

### 1. 模块级测试

直接对 `db.*` 做最小 C 程序测试：

- 查询存在 key
- 查询不存在 key
- 先删除再查询存在性

### 2. 命令层测试

通过服务端逻辑验证：

- `set foo bar`
- `exists foo`
- `del foo`
- `exists foo`

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
exists foo
del foo
exists foo
```

重点看：

- 新命令能否正确复用底层查找能力
- 不会破坏现有 `SET/GET/DEL`
