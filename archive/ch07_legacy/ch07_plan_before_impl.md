## 下一章目标

下一章建议聚焦在：

“围绕当前字符串 KV 主线，补上过期时间能力”

当前已经有：

- `SET`
- `GET`
- `DEL`
- `EXISTS`

但所有 key 现在都是永久存在的。
这和 Redis 很核心的一部分能力还差一截：

- key 可以设置过期时间
- 到期后再访问应当视为不存在

## 下一章结束后程序应具备什么能力

如果下一章按计划完成，程序应该具备这些能力：

- 继续支持当前所有基础命令
- 新增最小过期时间能力，例如 `EXPIRE key seconds`
- 新增最小剩余时间查询，例如 `TTL key`
- 已过期 key 在 `GET` / `EXISTS` / `DEL` 中会表现为不存在

## 需要新增或修改哪些文件

建议最小范围如下：

- 修改 `include/db.h`
  - 为节点增加过期时间字段
  - 增加过期相关接口，例如 `db_expire`、`db_ttl`
- 修改 `src/db.c`
  - 实现懒删除式过期检查
  - 在读、删、查存在性时处理已过期 key
- 修改 `src/tcp_server.c`
  - 在命令分发中增加 `EXPIRE` 和 `TTL`
- 更新 `README.md`
  - 更新项目阶段说明
- 新建或更新 `docs/ch07_notes.md`
  - 记录这一章设计、测试和学习重点

## 每个文件负责什么

- `include/db.h`
  - 定义数据库节点如何表示“有没有过期时间”
- `src/db.c`
  - 真正执行过期判断、设置过期时间、查询剩余 TTL
- `src/tcp_server.c`
  - 把 `EXPIRE` / `TTL` 接到命令层

## 哪些内容不能提前实现

为了保持章节清晰，下一章不应该提前做这些事：

- 不要做复杂的主动过期清理线程
- 不要做持久化
- 不要增加很多不相关命令
- 不要重写网络层

下一章只围绕“最小过期时间能力”展开。

## 如何测试下一章

下一章测试建议分成三层：

### 1. 模块级测试

直接对 `db.*` 做最小测试：

- 设置 key
- 给 key 设置过期时间
- 过期前读取
- 过期后读取
- 查询 TTL

### 2. 命令层测试

通过服务端逻辑验证：

- `set foo bar`
- `expire foo 1`
- `ttl foo`
- 等待后再 `get foo`
- `exists foo`

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

- 过期前还能读
- 过期后会变成 `(nil)` 或 `0`
- `ttl` 返回合理剩余值
