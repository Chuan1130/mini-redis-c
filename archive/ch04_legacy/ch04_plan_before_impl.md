## 下一章目标

下一章建议聚焦在：

“围绕当前存储层，补上删除能力和节点生命周期管理”

原因是：

- 当前已经有 `SET`
- 当前已经有 `GET`
- 哈希表也已经具备最小可用的扩容 / rehash

在这个基础上，最自然的下一步就是：

- 学会把 key 从哈希桶链中正确删掉
- 再把这个能力暴露成最小命令，例如 `DEL`

## 下一章结束后程序应具备什么能力

如果下一章按计划完成，程序应该具备这些能力：

- 继续支持 `SET key value`
- 继续支持 `GET key`
- 新增最小删除能力，例如 `DEL key`
- 删除后再次 `GET` 同一个 key 会返回不存在
- 存储层会正确维护链表中节点的摘除和内存释放

## 需要新增或修改哪些文件

建议最小范围如下：

- 修改 `include/db.h`
  - 增加删除接口声明，例如 `db_del`
- 修改 `src/db.c`
  - 实现桶链中的节点删除
  - 正确维护 `size`
  - 正确释放被删除节点的 key / value / node
- 修改 `src/tcp_server.c`
  - 在命令分发中增加 `DEL`
- 更新 `README.md`
  - 更新支持命令和阶段说明
- 新建或更新 `docs/ch04_notes.md`
  - 记录下一章设计、测试与学习重点

## 哪些内容不能提前实现

为了保持章节清晰，下一章不应该提前做这些事：

- 不要顺手增加很多命令
- 不要做 TTL / 过期
- 不要做持久化
- 不要改 RESP
- 不要重写客户端
- 不要大改网络层

下一章只围绕“删除能力”展开。

## 如何测试下一章

下一章测试建议分成三层：

### 1. 模块级基础测试

直接对 `db.*` 做最小 C 程序测试：

- 插入 key
- 删除存在 key
- 删除不存在 key
- 删除后再次查询
- 删除桶链中不同位置的节点

### 2. 模块级结构测试

重点验证：

- 删除桶头节点是否正确
- 删除链表中间节点是否正确
- 删除后 `size` 是否同步减少
- 删除后没有遗留悬挂链表指针

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
get foo
del foo
get foo
```

预期：

- `set foo bar` 成功
- `get foo` 返回 `bar`
- `del foo` 成功
- 再次 `get foo` 返回错误
