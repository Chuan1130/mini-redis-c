## 下一章目标

下一章建议聚焦在：

“继续完善当前哈希表实现，让它开始具备更完整的工程能力”

这一章不应该跳去做持久化或更多命令，
而应该继续把存储层这条主线走扎实。

## 下一章结束后程序应具备什么能力

如果下一章按计划完成，程序应该具备这些能力：

- 仍然支持当前 `SET key value` 和 `GET key`
- 当前哈希表不再只是固定桶数的教学演示版
- 能更系统地处理桶分布和容量变化
- 为后续继续扩展命令或数据结构打下更稳的地基

更具体地说，下一章最自然的能力目标是：

- 讨论并实现最小可用的扩容/rehash 思路

但这一步必须严格控制范围，只围绕当前哈希表主线展开。

## 需要新增或修改哪些文件

建议最小范围如下：

- 修改 `include/db.h`
  - 如果需要为扩容状态、桶数组切换等补充结构体字段，就在这里更新
- 修改 `src/db.c`
  - 这是下一章最核心的改动位置
  - 如果实现扩容/rehash，主要逻辑都会落在这里
- 更新 `README.md`
  - 更新当前项目阶段说明
- 新建或更新 `docs/ch03_notes.md`
  - 记录下一章设计、测试和学习重点

只有在确实有必要时，才考虑继续拆文件。
下一章不应为了“更工程化”而无理由增加过多文件。

## 哪些内容不能提前实现

为了保持章节清晰，下一章不应该提前做这些事：

- 不要顺手增加很多新命令
- 不要做 TTL / 过期
- 不要做持久化
- 不要改 RESP
- 不要重写客户端输入逻辑
- 不要大改 `tcp_server.c` 的网络层主流程

下一章只围绕“完善哈希表实现”展开。

## 如何测试下一章

下一章测试建议分成三层：

### 1. 模块级基础测试

直接对 `db.*` 做最小 C 程序测试：

- 写入新 key
- 覆盖已有 key
- 查找存在 key
- 查找不存在 key

### 2. 模块级结构测试

如果下一章实现扩容/rehash，需要重点测试：

- 插入大量 key 后仍能正确查回
- 扩容前后数据不丢失
- 扩容后覆盖更新仍然正确

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
get foo
set foo baz
get foo
get missing
```

预期行为应该和当前章节保持一致，
只是底层哈希表在规模增大时更加稳健。

那么可以原地少量注释保留，不必专门归档。
