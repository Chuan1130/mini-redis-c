# ch02_plan_before_impl

## 下一章目标

下一章建议聚焦在：

“把当前数组版存储层，推进为更像样的数据结构实现”

这一章的核心不是加很多新命令，而是继续沿着存储层主线前进。

## 下一章结束后程序应具备什么能力

如果下一章按计划完成，程序应该具备这些能力：

- 仍然支持当前 `SET key value` 和 `GET key`
- 存储层不再只依赖线性扫描查找
- key 的查找效率会比当前数组版更好
- 服务端主流程基本不需要大改，仍然通过 `db.*` 接口使用数据库

也就是说，下一章应该主要改变“数据库内部怎么找数据”，而不是改变“客户端如何发命令”。

## 需要新增或修改哪些文件

建议最小范围如下：

- 修改 `include/db.h`
  - 如果底层结构需要新的辅助类型，可以在这里补充声明
- 修改 `src/db.c`
  - 这是下一章最核心的改动位置
  - 把当前数组版实现升级成下一阶段的数据结构版本
- 修改 `docs/ch02_notes.md`
  - 记录下一章设计和测试
- 更新 `README.md`
  - 更新当前进度说明

如果新结构明显需要拆成多个文件，再考虑新增：

- `include/hash.h`
- `src/hash.c`

但这一步不能先默认做，必须先看下一章实现是否真的需要。

## 哪些内容不能提前实现

为了保持章节清晰，下一章不应该提前做这些事：

- 不要顺手增加很多新命令
- 不要做 TTL / 过期
- 不要做持久化
- 不要改成 RESP
- 不要重做客户端输入系统
- 不要把服务端网络层大拆大改

下一章只围绕“存储结构升级”展开。

## 如何测试下一章

下一章测试建议分两层：

### 1. 模块级测试

直接对 `db.*` 做最小 C 程序测试：

- 写入新 key
- 覆盖已有 key
- 查找存在 key
- 查找不存在 key
- 大量插入后再查找，确认仍然正确

### 2. 端到端测试

通过 `./server` 和 `./client` 验证：

```text
set foo bar
get foo
set foo baz
get foo
get missing
```

预期行为应与本章保持一致，只是内部实现更像样。

## 如果可能替换旧代码，应如何保留

如果下一章会替换掉本章 `src/db.c` 中较大的一段数组版实现，建议：

- 把本章的数组版实现移动到 `archive/ch02_legacy/`
- 文件头写清楚：
  - 这是哪一章的旧实现
  - 当时解决了什么问题
  - 为什么后来被替换
  - 新版本在哪个文件

如果只是很小的辅助函数改动，可以原地少量注释保留，不必专门归档。

## 下一章与本章的关键区别

本章的重点是：

- 把存储层从服务端主文件中独立出来

下一章的重点则应该是：

- 在已经独立的存储层内部，升级数据结构本身

简单说：

- 本章解决“边界”
- 下一章解决“结构”
