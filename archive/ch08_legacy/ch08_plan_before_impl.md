## 下一章目标

下一章建议聚焦在：

“围绕当前字符串 KV 主线，补上最小持久化能力”

当前已经有：

- 基础字符串命令
- 明确响应类型
- 最小过期时间能力

但服务端一旦退出，内存里的所有数据都会消失。

所以下一章最自然的推进点是：

- 能把当前数据库保存到本地文件
- 服务端重启时再从文件恢复

## 下一章结束后程序应具备什么能力

如果下一章按计划完成，程序应该具备这些能力：

- 支持最小快照保存，例如 `SAVE`
- 服务端启动时尝试从本地快照文件恢复数据
- 持久化中保留 key、value 和过期时间信息
- 已经过期的数据在恢复时不会继续当成有效数据

## 需要新增或修改哪些文件

建议最小范围如下：

- 新增 `include/persist.h`
  - 定义持久化接口
- 新增 `src/persist.c`
  - 实现保存和加载逻辑
- 修改 `src/tcp_server.c`
  - 启动时加载快照
  - 命令层加入 `SAVE`
- 修改 `include/db.h`
  - 如果需要，为遍历数据库节点补最小辅助接口
- 修改 `src/db.c`
  - 如果需要，为持久化遍历提供支持
- 更新 `README.md`
  - 更新项目阶段说明
- 新建或更新 `docs/ch08_notes.md`
  - 记录下一章设计、测试和学习重点

## 每个文件负责什么

- `include/persist.h`
  - 约定保存/加载接口
- `src/persist.c`
  - 真正把数据库写入文件、从文件读回
- `src/tcp_server.c`
  - 启动时加载，命令层里触发保存
- `db.*`
  - 继续只负责数据结构本身，必要时提供遍历支持

## 哪些内容不能提前实现

为了保持章节清晰，下一章不应该提前做这些事：

- 不要实现复杂 AOF
- 不要实现后台自动保存
- 不要做复制
- 不要大改事件循环

下一章只围绕“最小快照式持久化”展开。

## 如何测试下一章

下一章测试建议分成三层：

### 1. 模块级测试

直接测试保存和加载：

- 写入几个 key
- 设置部分 TTL
- 保存到文件
- 清空内存
- 再加载回来

### 2. 服务端启动测试

重点验证：

- 启动时能自动发现快照文件
- 加载后原有 key 能读回
- 已过期 key 不会被错误恢复

### 3. 端到端测试

通过 `./server` 和 `./client` 验证：

- `set foo bar`
- `save`
- 重启 server
- `get foo`
