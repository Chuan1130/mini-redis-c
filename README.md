# my_redis

这是一个按照《Build Your Own Redis》思路逐步实现的小型 C 语言项目。
目标不是一次性把功能堆满，而是把每一章的演进过程保留下来，方便回看和学习。

## 当前进度

当前项目已经完成了一个“网络层 + 协议层 + 可扩容哈希表存储层 + 基础字符串命令 + 更清晰响应语义 + 最小过期时间能力 + 最小持久化”的最小闭环：

- 服务端可以监听 TCP 端口并接收客户端连接。
- 服务端使用 `poll` 管理多个连接，并用非阻塞读写处理请求和响应。
- 客户端会把命令行输入编码成自定义二进制请求格式。
- 服务端会解析请求，执行最小命令集，并返回自定义二进制响应。
- 服务端中的内存 KV 已经从 `tcp_server.c` 中拆分到独立的 `db.*` 模块。
- `db.*` 的内部已经从“数组 + 线性扫描”升级成“哈希桶 + 链表”。
- 当前哈希表已经具备最小可用的扩容 / rehash 能力。
- 当前存储层已经具备最小删除能力，支持把 key 从桶链中正确移除。
- 当前项目已经具备最小存在性检查能力，可以直接判断 key 是否存在。
- 当前响应协议已经能明确区分 OK / ERR / STR / INT / NIL。
- 当前项目已经具备最小过期时间能力，支持 `EXPIRE` 和 `TTL`。
- 当前项目已经具备最小快照持久化能力，支持 `SAVE` 和启动时自动加载。
- 目前已支持的命令只有：
- `SET key value`
- `GET key`
- `DEL key`
- `EXISTS key`
- `EXPIRE key seconds`
- `TTL key`
- `SAVE`

这一阶段大致对应下面这些主题：

- TCP server
- client
- protocol framing
- request parsing
- command execution
- typed responses
- in-memory data structure（可扩容哈希表 + 基础字符串命令 + 最小过期时间）
- persistence（最小快照保存 / 启动恢复）

## 当前协议概览

### 1. 最外层传输格式

无论请求还是响应，最外层都遵循：

```text
[4字节长度][payload]
```

这里的 4 字节长度使用网络字节序，表示后面 payload 的字节数。

### 2. 请求 payload 格式

客户端会把一行命令拆成多个参数，然后编码为：

```text
[4字节 argc]
[4字节 arg1_len][arg1_bytes]
[4字节 arg2_len][arg2_bytes]
...
```

例如输入：

```text
set name redis
```

会被编码成 3 个参数：`set`、`name`、`redis`。

### 3. 响应 payload 格式

服务端当前返回：

```text
[4字节 type][按 type 不同而变化的后续字段]
```

当前主要响应类型有：

- `RESP_OK`：简单成功
- `RESP_ERR`：错误
- `RESP_STR`：字符串结果
- `RESP_INT`：整数结果
- `RESP_NIL`：空结果 / 不存在

## 如何编译

```bash
make
```

会生成两个可执行文件：

- `./server`
- `./client`

## 如何运行

先启动服务端：

```bash
./server
```

再启动客户端：

```bash
./client
```

然后在客户端中输入：

```text
set foo bar
get foo
```

## 当前已知局限

这些局限是当前阶段刻意保留的，后续会按章节逐步改进：

- 当前哈希表虽然已经支持最小 rehash、删除、存在性检查和过期时间，但仍然是教学用的简化版本，还没有做更完整的渐进式迁移等能力。
- 当前仍然没有更复杂的 AOF、复制、事务和更多数据类型。
- 客户端当前按空格切分输入，不适合带空格参数。
- 服务端里还保留了一段旧的 `PING / ECHO` 遗留逻辑，当前并不走主路径，后续适合归档到 `archive/`。
- 当前虽然已经进入哈希桶章节，但还没有实现更完整的哈希表工程细节。
